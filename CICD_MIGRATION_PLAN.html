2
Pre-extraction audit — run before any file is moved
new · Claude Code
›
For each persona repo, Claude Code runs a cross-directory import scan on both frontend and backend source trees:
# Scan for imports that escape the persona's own src/
grep -rn "from ['\"]\.\./" <persona>/frontend/src/
grep -rn "require(['\"]\.\./" <persona>/frontend/src/
grep -rn "from ['\"]\.\./" <persona>/backend/src/

# Also scan for absolute path aliases that point outside src/
grep -rn "@shared\|@common\|@core\|@utils" <persona>/frontend/src/
grep -rn "@shared\|@common\|@core\|@utils" <persona>/backend/src/
›
Claude Code produces an audit report listing every offending import with its file path and line number, grouped by persona.
›
Specifically flag any signup, auth, or account-creation files that import from outside their own persona boundary — these are the highest-risk files given the different signup logic per persona.
✓ If audit is clean
Proceed directly to Phase 3. No remediation needed — each persona is already self-contained.
⚠ If offending imports found
Claude Code inlines the shared dependency into each persona's own src/ before extraction. Each persona gets its own copy — no cross-persona imports in the final state.
Signup logic in particular: if two personas share a common auth helper (e.g. a ../../shared/auth/validators.ts), Claude Code must copy it into each persona separately and update the import path — not create a shared folder in the target repo. The CI pipeline has no concept of cross-system shared code; each app must build independently.
Path aliases (e.g. @/components in tsconfig.json) are fine as long as they resolve within the persona's own folder. Claude Code must verify the paths mapping in each tsconfig.json and next.config.ts to confirm they don't point outside src/.
3
Backend extraction — per persona, repeat ×4
Claude Code · trini-thrive-be
›
Create hopecard/<persona>/ in trini-thrive-be.
›
Copy src/, tests/, package.json, tsconfig.json, nest-cli.json, eslint.config.mjs, .prettierrc, Dockerfile, render-build.sh, sonar-project.properties from the persona backend. Exclude node_modules, .env, .git.
›
Update sonar-project.properties: set a unique sonar.projectKey e.g. hopecard-admin-be.
›
Append persona env vars to root .env.example under a # hopecard-<persona> comment block.
›
Run npm install && npm run lint && npm run typecheck && npm run build && npm run test:cov inside each persona folder. All must pass before moving to the next persona.
Each persona is its own NestJS app — its own package.json and independent build. Do not merge the four backends. The signup controllers, DTOs, and validation logic for each persona remain untouched inside their own src/.

The pipeline treats each persona folder as an independent system — separate lint, build, test, and deploy per persona. A failure in one persona does not block the others from being reported, but will block promotion of the whole PR.
