Cross-system conflict prevention — mandatory for every module you add
✕ Conflict risk — what breaks other systems
Two modules from different systems export a class with the same name (e.g. both export AuthService). NestJS resolves providers by token — if tokens collide, one system's service silently overwrites the other's in the DI container. The broken system's tests may still pass if mocks shadow the collision, making this invisible until runtime.
✓ Prevention — required naming pattern
Prefix every exported class, provider token, and controller with your system and persona identifier. Never use bare generic names. Example: HopecardDonorAuthService not AuthService. The module folder name is not enough — the class name inside it must also be unique within your service.
✕ Conflict risk — duplicate global middleware or guards
Registering a guard or middleware globally in your service's app.module.ts (e.g. via APP_GUARD or APP_INTERCEPTOR) applies it to every route in that service. If a guard rejects requests unexpectedly, debugging becomes difficult. Keep guards scoped to specific controllers or routes.
✓ Prevention — scope guards to your own controllers
Never register your guards or interceptors globally via APP_GUARD / APP_INTERCEPTOR in app.module.ts. Apply them at the controller level using @UseGuards() or at the module level inside your own module only. Global registration is reserved for shared infra in src/common/.
✕ Conflict risk — duplicate route paths
Two controllers from different systems registering the same HTTP route (e.g. both have @Get('/campaigns') without a controller-level prefix) will have one silently shadow the other. NestJS registers both but only the last one loaded wins.
✓ Prevention — controller prefix mandatory
Every controller must have a @Controller('prefix') decorator with a unique route prefix that identifies the system and persona. Example: @Controller('hopecard/beneficiary/auth'). Never use a bare @Controller() or a generic prefix that another system might also use.
✕ Conflict risk — duplicate module imports in app.module.ts
Importing the same shared module twice (e.g. SupabaseModule imported directly in app.module.ts by two different systems' migrations) can cause duplicate provider registration warnings and unexpected singleton behaviour.
✓ Prevention — import shared modules inside your own module only
Import SupabaseModule, CommonModule, and other shared modules inside your own module file (e.g. BeneficiaryAuthModule), not directly in app.module.ts. NestJS deduplicates modules when they are imported through the module graph — direct root-level imports bypass this.
Isolation rule — backend: the only files your migration may create or modify are your own new module folders inside src/ and the import list in src/app.module.ts. No other file in trini-thrive-be is yours to touch. If you discover a bug in a shared module, report it to the CICD handlers — do not fix it unilaterally. Changes to shared infrastructure affect all three systems.
No per-persona config files. Do not create additional package.json, tsconfig.json, Dockerfile, or sonar-project.properties inside your module folders. One of each exists at the repo root. The pipeline does not look for extras and their presence confuses Gate 3.
Shared module reuse — import, never copy. If src/supabase/ covers your needs, import SupabaseModule inside your own module file via NestJS DI. Do not copy supabase.service.ts into your module folder. Duplicates create divergence, double maintenance surface, and DI token collisions.
3B
Persona claim enforcement — JWT routing safety
Claude Code · trini-thrive-be · mandatory
›
Why this is required. In a microservices architecture, each service must validate that incoming requests have the correct JWT claims for that service. Without explicit persona and system claims in the JWT, a frontend user could manually change the URL to access a different persona (e.g., a Donor user typing /hope-card/admin) without proper authorization. Backend validation + frontend middleware together prevent this security risk.
›
Every auth service that issues a JWT must include two mandatory claims:
Required JWT payload shape — apply to every auth service in src/
// Every persona's auth service must issue tokens with these claims
// In addition to the existing claims (sub, email, role, exp, iat)

const payload = {
  sub: user.id,
  email: user.email,
  persona: '[persona-slug]', // lowercase hyphenated · unique per persona
  system: '[system-slug]', // lowercase hyphenated · identifies the system
};

// Hopecard examples:
// beneficiary-auth → persona: 'beneficiary', system: 'hopecard'
// cm-auth → persona: 'campaign-manager', system: 'hopecard'
// donor-auth → persona: 'digital-donor', system: 'hopecard'
// admin-auth → persona: 'admin', system: 'hopecard'
›
Update the JWT payload DTO or interface (if one exists in the codebase) to declare persona and system as required string fields. This ensures TypeScript enforces the claims at compile time across every auth service.
›
If a shared JWT strategy or guard exists in src/common/ that validates tokens, update it to read and expose the persona and system claims on the request object so downstream controllers and guards can access them without decoding the token again:
// In src/common/guards/jwt.guard.ts or jwt.strategy.ts
// After token validation, attach claims to request
validate(payload: JwtPayload) {
  return {
    userId: payload.sub,
    email: payload.email,
    persona: payload.persona, // expose to all controllers
    system: payload.system, // expose to all controllers
  };
}
›
Apply the persona and system values that match your system. For systems other than Hopecard — confirm the correct persona slug values with your system team before adding them. Never guess persona slugs for another system's auth services.
›
Update spec files. Every auth service spec must assert that the issued token contains the correct persona and system values. A test that does not assert these claims is incomplete and must be treated as a test gap:
// In beneficiary-auth/auth.service.spec.ts
it('should issue a token with persona and system claims', async () => {
  const result = await service.login(mockUser);
  const decoded = jwtService.decode(result.access_token);
  expect(decoded.persona).toBe('beneficiary');
  expect(decoded.system).toBe('hopecard');
});
Backend MUST validate persona and system claims. Every protected endpoint must check that the JWT persona and system claims match the expected values for that service. If claims mismatch, return 403 Forbidden. This prevents a user from accessing an endpoint outside their authorized persona, even if they manually change the URL. This is a security requirement, not optional.
Never change or remove existing claims (sub, email, role, exp, iat). Only add persona and system. Changing existing claims will break any frontend or middleware that already reads them.
For other systems (Damayan, BayaniHub): when their auth services are migrated, the same rule applies. Every auth service must include persona and system claims using their own system and persona slug values. This is not Hopecard-specific — it is an architecture-wide requirement for all microservices.

Step E — Next.js middleware for persona route enforcement
›
Create a single middleware.ts at [system-folder]/src/middleware.ts that enforces persona routing at the framework level. This is the architectural guarantee that makes cross-persona misdirection impossible — it runs before any page renders:
// [system-folder]/src/middleware.ts
import { NextRequest, NextResponse } from 'next/server';

// Map each URL prefix to its expected persona slug
const PERSONA_PREFIX_MAP: Record<string, string> = {
  '/admin': 'admin',
  '/beneficiary': 'beneficiary',
  '/donor': 'digital-donor',
  '/campaign-manager': 'campaign-manager',
};

// Public routes that do not require auth — login and register pages
const PUBLIC_ROUTES = ['/login', '/register', '/forgot-password'];

export function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;

  // Determine which persona prefix this request belongs to
  const prefix = Object.keys(PERSONA_PREFIX_MAP)
    .find(p => pathname.startsWith(p));

  if (!prefix) return NextResponse.next();

  // Allow public routes without auth
  const isPublic = PUBLIC_ROUTES.some(r => pathname.endsWith(r));
  if (isPublic) return NextResponse.next();

  // Read stored persona from cookie or header
  const storedPersona = request.cookies.get('persona')?.value;
  const expectedPersona = PERSONA_PREFIX_MAP[prefix];

  // No auth at all — redirect to this persona's login
  if (!storedPersona) {
    return NextResponse.redirect(new URL(`${prefix}/login`, request.url));
  }

  // Wrong persona — redirect to correct persona's login, never another persona's home
  if (storedPersona !== expectedPersona) {
    return NextResponse.redirect(new URL(`${prefix}/login`, request.url));
  }

  return NextResponse.next();
}

export const config = {
  matcher: ['/admin/:path*', '/beneficiary/:path*', '/donor/:path*', '/campaign-manager/:path*'],
};
Step F — Persona storage strategy per persona type
›
Not all personas issue JWTs — the storage strategy differs based on how the backend authenticates each persona. Apply the correct pattern per persona:
// PATTERN 1 — JWT-issuing personas (e.g. Admin)
// Read persona and system from the JWT claim after login
const decoded = JSON.parse(atob(token.split('.')[1]));
if (decoded.persona !== 'admin' || decoded.system !== 'hopecard') {
  clearAuth(); router.push('/admin/login'); return;
}
document.cookie = `persona=admin; path=/; SameSite=Strict`;
router.push('/admin/dashboard');

// PATTERN 2 — Supabase-session personas (Beneficiary, Digital Donor, Campaign Manager)
// Backend returns a Supabase session, not a JWT with persona claims
// Store the persona slug at login time — derived from which endpoint was called
const { data, error } = await supabase.auth.signInWithPassword(credentials);
if (error || !data.session) { /* handle error */ return; }
// The login page already knows which persona it is — store it explicitly
document.cookie = `persona=beneficiary; path=/; SameSite=Strict`; // or 'digital-donor', 'campaign-manager'
router.push('/beneficiary/dashboard');
Why a cookie instead of localStorage for persona storage: Next.js middleware runs on the server edge and cannot read localStorage. The middleware needs to read the persona to enforce routing before the page renders. A SameSite=Strict cookie with no sensitive data (persona slug only — not the auth token) is the correct mechanism for this. The actual auth token (JWT or Supabase session) is stored separately using whatever the persona's existing auth implementation uses.
