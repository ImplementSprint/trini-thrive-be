Architectural rules — confirmed by CICD handlers
▸
True microservices via NestJS monorepo. Each persona is its own app under apps/ with its own main.ts, Dockerfile, and independent port. Not a monolith.
▸
Shared code lives in libs/. Common utilities, Supabase client, API Center SDK, and contracts are shared libraries — never duplicated across apps.
▸
Services must be under apps/. The CICD handler's most critical requirement. No exceptions. Every runnable persona service is an app entry point.
▸
JWT persona + system claims are mandatory. Every auth service issues tokens with persona and system claims. Every protected endpoint validates them via PersonaGuard. Mismatch = 403.
▸
No .env committed. .env.example lists key names only. Devs create .env locally. Deployed values go to the API tribe. Migration never auto-transfers .env.
▸
Branch flow: local branch (from test) → PR to develop (sandbox) → PR to test (CICD governance) → auto uat → auto main. develop is an internal convention, not an official governed branch.

How the NestJS monorepo achieves microservices
›
Each folder under apps/ is a fully independent NestJS application registered in nest-cli.json. It has its own main.ts (its own port), its own root module, its own tsconfig.app.json extending the root, and its own Dockerfile.
›
Shared code lives in libs/ and is imported via TypeScript path aliases (e.g. @app/common, @app/supabase) defined in the root tsconfig.json. Nothing in libs/ is runnable — it is consumed by apps.
›
Each app is built independently: nest build [app-name]. Each app is deployed independently. Each app runs on its own port and its own Render service. There is no shared runtime between personas.
›
The ACTIVE_SERVICE env var pattern from earlier specs is no longer needed — the monorepo structure achieves true process isolation natively. Each app is its own entry point.
nest-cli.json — register every app (example)
{
  "monorepo": true,
  "root": "apps/api",
  "projects": {
    "api": { "type": "application", "root": "apps/api", "sourceRoot": "apps/api/src" },
    "location-service": { "type": "application", "root": "apps/location-service" },
    // Add your persona apps here
    "[system]-[persona]": { "type": "application", "root": "apps/[system]-[persona]", "sourceRoot": "apps/[system]-[persona]/src" },
    // Repeat for each persona
  }
}
Every new app must be registered in nest-cli.json or the NestJS build system will not recognise it. This is the first thing to do after creating a new app folder. The pipeline discovers apps via this file.

3B
JWT persona claims + PersonaGuard — mandatory security layer
Claude Code · trini-thrive-be · never skip
›
Why this is required. Even with separate apps on separate ports, a malicious or misconfigured client could send a valid JWT from one persona to another persona's endpoint. The PersonaGuard closes this gap at the application layer — every protected endpoint rejects tokens whose persona claim does not match its own expected persona.
JWT payload — required claims for every auth service
// Every persona's auth service must include these two claims
const payload = {
  sub: user.id,
  email: user.email,
  persona: '[persona-slug]', ← lowercase hyphenated · unique per persona
  system: '[system-slug]', ← lowercase hyphenated · identifies the system
};

// Hopecard reference values:
// admin-auth → persona: 'admin', system: 'hopecard'
// donor-auth → persona: 'digital-donor', system: 'hopecard'
// cm-auth → persona: 'campaign-manager', system: 'hopecard'
// beneficiary-auth → persona: 'beneficiary', system: 'hopecard'
PersonaGuard — lives in libs/common/src/guards/
// libs/common/src/guards/persona.guard.ts
@Injectable()
export class PersonaGuard implements CanActivate {
  constructor(private reflector: Reflector) {}

  canActivate(ctx: ExecutionContext): boolean {
    const { expectedPersona, expectedSystem } =
      this.reflector.get('persona_meta', ctx.getHandler());
    const user = ctx.switchToHttp().getRequest().user;

    if (!user?.persona || !user?.system) {
      throw new ForbiddenException({ code: 'INVALID_CLAIMS' });
    }
    if (user.persona !== expectedPersona || user.system !== expectedSystem) {
      throw new ForbiddenException({ code: 'PERSONA_MISMATCH' });
    }
    return true;
  }
}

// Response body NEVER leaks expected values — only the code
// { "statusCode": 403, "message": "Access denied", "code": "PERSONA_MISMATCH" }
JwtGuard implementation note: the guard at libs/common/src/guards/jwt.guard.ts is a custom CanActivate implementation using jose's jwtVerify — it is NOT a Passport strategy. There is no validate() method and no jwt.strategy.ts. Do not reference or create a Passport-style strategy. The guard verifies the token, attaches the full payload to request.user, and exposes all claims (including persona and system) to downstream controllers.
Already complete for Hopecard — do not re-apply:
✅ JwtPayload interface already declares persona: string and system: string in libs/common/src/guards/jwt.guard.ts (lines 10–18)
✅ JwtGuard.canActivate already validates persona !== expectedPersona || system !== 'hopecard' and throws 403 (lines 50–53)
✅ request.user = payload already exposes all claims to controllers (line 56)
These items are complete. New systems migrating after Hopecard inherit this implementation automatically.

Step C — Next.js middleware: persona route enforcement
// [system]/src/middleware.ts — prevents URL-switching exploits
const PERSONA_MAP: Record<string, string> = {
  '/admin': 'admin', '/donor': 'digital-donor',
  '/campaign-manager': 'campaign-manager', '/beneficiary': 'beneficiary',
};
const PUBLIC = ['/login', '/register', '/forgot-password'];

export function middleware(req: NextRequest) {
  const prefix = Object.keys(PERSONA_MAP).find(p => req.nextUrl.pathname.startsWith(p));
  if (!prefix) return NextResponse.next();
  if (PUBLIC.some(r => req.nextUrl.pathname.endsWith(r))) return NextResponse.next();

  const stored = req.cookies.get('persona')?.value;
  if (!stored || stored !== PERSONA_MAP[prefix]) {
    return NextResponse.redirect(new URL(`${prefix}/login`, req.url));
  }
  return NextResponse.next();
}
export const config = { matcher: ['/admin/:path*', '/donor/:path*', '/campaign-manager/:path*', '/beneficiary/:path*'] };
Step D — Persona cookie storage strategy (per persona type)
// JWT-issuing personas (e.g. Admin) — read from token claim

Step E — Logout: persona cookie must be cleared on every sign-out
›
Why this matters. The middleware reads the persona cookie to decide whether to allow or redirect a request. If a user logs out but the cookie is not cleared, the next person who opens the same browser will have a stale persona cookie from the previous session. If they try to log in as a different persona (e.g. previous user was donor, new user is admin), the middleware will redirect them away from /admin/* until the old cookie expires naturally. Clearing it on logout prevents this entirely.
›
Every persona's logout handler must clear both the auth token and the persona cookie before redirecting to login:
// In every persona's logout handler — order matters
// 1. Clear the auth token (JWT or Supabase session)
clearAuthToken(); // remove from localStorage / sessionStorage / httpOnly cookie
supabase.auth.signOut(); // if Supabase-session persona

// 2. Clear the persona cookie explicitly — set Max-Age=0 to expire it immediately
document.cookie = `persona=; path=/; SameSite=Strict; Max-Age=0`;

// 3. Only redirect AFTER both are cleared
router.push('/[persona-prefix]/login');

// NEVER redirect before clearing — the middleware reads the cookie
// synchronously on the next request. A stale cookie means the new
// user gets redirected away from their intended persona login page.
Never rely on cookie expiry to clear persona state. The persona cookie must be explicitly expired with Max-Age=0 on every logout. Do not set a long-lived expiry on the persona cookie — it should last only as long as the session. If the auth token expires or is revoked, the persona cookie must be cleared simultaneously, not left to expire on its own schedule.
Cross-persona login scenario: if a browser has a stale persona=digital-donor cookie and someone navigates directly to /admin/login, the middleware will redirect them to /admin/login (the login page is public so it passes through). The admin login page must call the logout handler on mount if a mismatched persona cookie is detected — this clears the stale cookie before the new login proceeds.
Step F — Port registry: prevent duplicate service ports locally
›
Why this matters. Since each persona service runs as its own NestJS process on its own port, two services accidentally assigned the same port will cause a bind error on startup — one service will fail to start and all its routes will be unreachable. In a docker-compose setup this causes the conflicting container to exit immediately. Port assignments must be unique across every service in the monorepo and must be documented in one canonical place.
›
Canonical port registry — maintain this in .env.example and docker-compose.yml. Every system must consult the registry before assigning ports and must not claim a port already listed:
# PORT REGISTRY — trini-thrive-be

Each service's main.ts reads its own dedicated port env var — never a generic PORT that could be accidentally shared between services running simultaneously:
// apps/hopecard-admin-service/src/main.ts
const port = process.env.HOPECARD_ADMIN_PORT ?? 3101;

// apps/hopecard-donor-service/src/main.ts
const port = process.env.HOPECARD_DONOR_PORT ?? 3104;

// Never: process.env.PORT — this is ambiguous when multiple services
// run simultaneously and the same PORT env var is set in the shell.
›
Before starting any local multi-service session, verify no port is already bound:
# Check if a port is already in use before starting services
# Windows
netstat -ano | findstr :3101
# macOS / Linux
lsof -i :3101

# If a port is bound by a leftover process, find and kill it
# Windows: taskkill /PID [pid] /F
# macOS / Linux: kill -9 [pid]

# With docker-compose — conflicting ports surface at startup
docker-compose up # will fail with "port is already allocated" if conflict exists
docker-compose down # always run this before re-starting to release all ports
When a new system (Damayan, BayaniHub) migrates their services, they must check the port registry in .env.example before assigning any port, claim a port range for their system, and add their entries to both .env.example and docker-compose.yml. Never pick a port by guessing — always consult the registry first.
docker-compose ports mapping must exactly match the service's env var default. If HOPECARD_ADMIN_PORT=3101 then docker-compose.yml must have ports: ["3101:3101"] and environment: HOPECARD_ADMIN_PORT: "3101". A mismatch between the published port and the port the process binds to will make the service unreachable from the host even if the container starts successfully.
