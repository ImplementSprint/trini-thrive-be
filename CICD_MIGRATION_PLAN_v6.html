Applies to all systems in the ImplementSprint org
This plan is written for any system migrating their personas into the shared CICD repositories. Replace [system] and [persona] placeholders throughout with your own system and persona names. Each system has a unique set of personas and services — this plan does not prescribe what those are, only how to structure and integrate them. Your work must never reach outside your own system's designated folders.
Hopecard → hope-card/ Damayan → damayan/ BayaniHub → bayani-hub/
Key structural rules — confirmed by compliance history and repo file structures
▸
Backend: one NestJS monolith for the whole org. All persona modules from all systems go flat into src/. One build, one Docker image, one deploy.
▸
Frontend: one Next.js app per system. All personas for a system are merged flat into that system's src/. Not one app per persona.
▸
Branch flow: local branch (from test) → PR to develop (shared sandbox) → PR to test (CICD governance). Never push directly to test, uat, or main.
▸
Strict isolation: your migration must never create, modify, or delete any file outside your own system's folders. Verify before every commit with git diff develop --name-only.
▸
No .env committed ever. Migration never auto-transfers .env files. Devs create their own .env locally from .env.example. Deployed values go to the API tribe only.
▸
Cross-system conflict prevention is mandatory. Every module, provider, DI token, and controller in the monolith must be uniquely named. Conflicts in the shared src/ break all systems, not just yours.

◆
local branch — created from test. All migration work happens here. Never commit directly to any shared branch.
◆
develop — shared sandbox for all three systems. Chaotic by design. PRs here are for integration visibility and conflict discovery between system teams. No CICD governance runs here. PR authors cannot self-approve.
◆
test — all 12 CICD pipeline gates run here. This is the governance checkpoint. Only promote from develop to test when your work is clean, tested locally, and passes all pre-push checks.
◆
uat → main — auto-promoted by the pipeline once all gates pass on test. No manual action required after that.
Do not skip develop. The develop branch exists specifically to surface cross-system conflicts before governance runs. Pushing directly from your local branch to test bypasses the shared sandbox and risks failing the pipeline with issues that could have been caught earlier. Resolve all conflicts in develop first.

✓ Audit clean
Proceed to Phase 3. Naming is confirmed unique, shared services decision made, route list compiled.
⚠ Issues found
Fix before extraction: inline deps, replace localhost URLs, resolve naming collisions, pair @Optional() with @Inject(Token).
NestJS DI union type rule: any constructor parameter typed as SomeClass | null with @Optional() must also have @Inject(SomeClass). Without it, emitDecoratorMetadata emits Object — NestJS resolves to undefined at test time, causing silent failures where mocked values are never injected. Fix: @Optional() @Inject(MyService) private readonly svc: MyService | null.

›
Run npm audit fix after installing. Gate 7 fails on any high or critical CVE. Commit the updated package-lock.json.
Cross-system conflict prevention — mandatory for every module you add
✕ Conflict risk — what breaks other systems
Two modules from different systems export a class with the same name (e.g. both export AuthService). NestJS resolves providers by token — if tokens collide, one system's service silently overwrites the other's in the DI container. The broken system's tests may still pass if mocks shadow the collision, making this invisible until runtime.
✓ Prevention — required naming pattern
Prefix every exported class, provider token, and controller with your system and persona identifier. Never use bare generic names inside a shared monolith. Example: HopecardBeneficiaryAuthService not AuthService. The module folder name is not enough — the class name inside it must also be unique.
✕ Conflict risk — duplicate global middleware or guards
Registering a guard or middleware globally in app.module.ts (e.g. via APP_GUARD or APP_INTERCEPTOR) applies it to every route in the monolith — including other systems' routes. One system's auth guard silently protecting another system's public endpoints will cause unexpected 401s.
✓ Prevention — scope guards to your own controllers
Never register your guards or interceptors globally via APP_GUARD / APP_INTERCEPTOR in app.module.ts. Apply them at the controller level using @UseGuards() or at the module level inside your own module only. Global registration is reserved for shared infra in src/common/.
✕ Conflict risk — duplicate route paths
Two controllers from different systems registering the same HTTP route (e.g. both have @Get('/campaigns') without a controller-level prefix) will have one silently shadow the other. NestJS registers both but only the last one loaded wins.
✓ Prevention — controller prefix mandatory
Every controller must have a @Controller('prefix') decorator with a unique route prefix that identifies the system and persona. Example: @Controller('hopecard/beneficiary/auth'). Never use a bare @Controller() or a generic prefix that another system might also use.
✕ Conflict risk — duplicate module imports in app.module.ts
Importing the same shared module twice (e.g. SupabaseModule imported directly in app.module.ts by two different systems' migrations) can cause duplicate provider registration warnings and unexpected singleton behaviour.
✓ Prevention — import shared modules inside your own module only
Import SupabaseModule, CommonModule, and other shared modules inside your own module file (e.g. BeneficiaryAuthModule), not directly in app.module.ts. NestJS deduplicates modules when they are imported through the module graph — direct root-level imports bypass this.
Isolation rule — backend: the only files your migration may create or modify are your own new module folders inside src/ and the import list in src/app.module.ts. No other file in trini-thrive-be is yours to touch. If you discover a bug in a shared module, report it to the CICD handlers — do not fix it unilaterally. Changes to shared infrastructure affect all three systems.
No per-persona config files. Do not create additional package.json, tsconfig.json, Dockerfile, or sonar-project.properties inside your module folders. One of each exists at the repo root. The pipeline does not look for extras and their presence confuses Gate 3.
Shared module reuse — import, never copy. If src/supabase/ covers your needs, import SupabaseModule inside your own module file via NestJS DI. Do not copy supabase.service.ts into your module folder. Duplicates create divergence, double maintenance surface, and DI token collisions.

Backend tests and coverage configuration
Claude Code · trini-thrive-be
›
Write *.spec.ts files for every in-scope (prioritised) module. Target: ≥80% line coverage across covered files — measured from coverage/coverage-summary.json by Gate 6.
›
Update coveragePathIgnorePatterns in package.json — add your deprioritised module exclusions. Never remove or reorder exclusions added by other systems. Only append yours at the end of the array.
coveragePathIgnorePatterns — required baseline + your additions
"coveragePathIgnorePatterns": [
  // Always present — never remove
  "/node_modules/", "/coverage/", "/dist/",
  "src/main.ts", "\\.module\\.ts$", "__mocks__",
  "\\.dto\\.ts$", "\\.entity\\.ts$", "\\.interface\\.ts$",
  "/api-center/", "/common/decorators/", "/common/guards/",
  // Existing exclusions from other systems — do NOT remove
  "... existing entries from other systems ...",
  // ↓ Append your deprioritised modules below
  "/[your-deprioritised-module-a]/",
  "/[your-deprioritised-module-b]/"
]
›
After updating patterns, run npm run test:cov and inspect the printed summary. Confirm your patterns exclude exactly what you intend — no more, no less.
›
Coverage reporters must include json-summary and lcov. Test reporter must be jest-junit outputting to test-results/junit.xml. These are pipeline requirements — do not change the reporters config.
Pattern precision matters critically in a shared monolith. A pattern like /auth/ is dangerously broad — it would exclude every module containing "auth" in its path, potentially swallowing tested modules from other systems. Always use the most specific segment: /donor-auth/ not /auth/, /cm-auth/ not /auth/.
SonarCloud blocker rules — Gate 9:
· Async helpers must be at module scope, not nested inside describe blocks (rule S7721)
· No redundant type assertions — {} as Partial<T> where {} already satisfies Partial<T> (rule S4325)
Either will fail Gate 9 and block the PR for all systems — not just yours.
Never remove coverage exclusions added by other systems. Removing another system's exclusion pulls their untested deprioritised modules back into the coverage calculation. This can drop the overall coverage below 80% and fail Gate 6 for the whole repo — blocking every system's PR, not just yours.

Frontend extraction — merge all personas into your system's src/
Claude Code · trini-thrive-fe
›
Your system has one Next.js app, not one per persona. All personas are merged flat into [system-folder]/src/. The existing system folder in the repo already has the correct scaffolding — merge into it, never replace it.
›
Map routes before moving files. Use the route list from Phase 2. For each persona, decide its destination path in [system-folder]/src/app/ before touching anything.
›
Route conflict resolution: if two personas share the same route path, use Next.js route groups. A route group folder wrapped in parentheses is invisible to the router — it namespaces the filesystem without changing the public URL:
# Two personas both have /dashboard — resolve with route groups
[system]/src/app/
├── (persona-a)/
│   └── dashboard/
│       └── page.tsx → public URL: /dashboard (persona A)
└── (persona-b)/
    └── dashboard/
        └── page.tsx → public URL: /dashboard (persona B)
›
Merge approach — per persona:
·
Copy src/app/ contents into [system-folder]/src/app/ preserving directory structure. Use route groups for path conflicts.
·
Copy src/lib/, src/components/, src/hooks/, src/utils/ etc. into the system's src/. If a folder name collides with another persona's, prefix it with the persona name (e.g. src/admin-components/ vs src/donor-components/).
·
Copy public/ assets into [system-folder]/public/. Prefix asset subfolder names if collision exists.
·
Merge package.json dependencies — add packages the persona requires that aren't already present. Never downgrade an existing package version.
·
Do not copy node_modules, .env, .git, dist, or .next from source repos.
›
Replace all hardcoded localhost API URLs with process.env.NEXT_PUBLIC_*. Do not rename existing env var keys already referenced in the code.
›
Run from inside [system-folder]/: npm install && npm run lint && npm run test && npm run build. All must pass before Phase 6.
Isolation rule — frontend: you may only create or modify files inside [your-system-folder]/. Never touch another system's folder. Never modify tests/performance/, sonar-project.properties, or .github/workflows/ at the repo root. Run git diff develop --name-only before committing and verify every changed file is inside your system folder.
Routing verification is mandatory before pushing. After the build passes, manually walk every route from the Phase 2 checklist and confirm it resolves correctly. A silently broken route must be caught before the PR is opened — not discovered after the pipeline runs or after merge to develop.
The existing system scaffold is the host app. The src/app/layout.tsx, jest.config.js, next.config.ts, and other root-level config files in your system folder are already correctly wired. Merge persona code into them — never wholesale replace them with a persona's own config versions.
